# Реалізація частини 3

Реалізовано всі 8 операцій контракту `openapi.yaml` версії 0.3.0. Інтерактивна документація читає цей файл при запуску, без копії специфікації в JS. Службових маршрутів для імітації помилок немає.

## Структура та асинхронність

`main.js` містить Express, маршрути, перевірку вхідних даних, єдину обробку помилок, Base62, запуск HTTP та завершення роботи. `db.js` містить пул pg-promise, SQL і транзакції. `healthcheck.js` об'єднує SELECT 1, HTTP-обробник `/health` та HTTP-пробу Docker; при прямому запуску виконується тільки проба. `src/config.js` зберігає dotenv, commander та валідацію конфігурації.

Мережеві й файлові операції очікуються через `await`. Тіло запиту читається через асинхронний ітератор, запуск і закриття HTTP — через проміси подій `once`. Транзакція виконується явно через BEGIN/COMMIT/ROLLBACK на одному з'єднанні, без callback `db.tx`; з'єднання звільняється у finally. Єдиний анонімний callback прикладного коду — передавання запиту Express у `http.createServer()`. Валідація та форматування — синхронні функції без вводу-виводу; Express і події процесу отримують іменовані async-обробники.

Усі функції та важливі ділянки серверного коду мають українські коментарі. `src/app.js`, `src/db.js` і `scripts/healthcheck.js` прибрано, щоб уникнути паралельних реалізацій.

## Base62, повторні URL та колізії

Автоматичний код має 8 символів із `ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789`: 62^8 можливих значень. `crypto.randomInt(62)` рівномірно обирає символ і не має зміщення, властивого простому остачному діленню випадкового байта на 62. Це випадкові коди, а не послідовне кодування ID: вони не розкривають порядок і кількість створень.

Без alias спочатку шукаємо найстаріше посилання для нормалізованого URL (`created_at ASC, id ASC`). Знайдений ресурс повертаємо з 200 і Location, зберігаючи code, createdAt та clicks. Генератор у цьому випадку не викликається. Новий ресурс дає 201. Явний вільний alias створює окремий ресурс; зайнятий дає 409 навіть для того самого URL.

Транзакційне advisory-блокування хешу URL серіалізує конкурентне створення однакової адреси. Колізія самого хешу лише зайвий раз серіалізує різні URL. Остаточна унікальність code забезпечується PostgreSQL UNIQUE: INSERT ... ON CONFLICT DO NOTHING не руйнує транзакцію. Випадкову колізію повторюємо максимум 5 разів, далі 500. Для явного alias колізія відразу дає 409. PATCH може змінити URL на адресу іншого ресурсу; тому UNIQUE для original_url не вводимо. Повторний POST без alias надалі обере найстаріший із таких ресурсів.

Схему БД змінювати не потрібно. Наявний volume і дані сумісні з реалізацією; автоматичні коди попередніх форматів і alias з `_` чи `-` залишаються дозволеними контрактом Code.

## Перевірка запитів та відповіді

POST/PATCH спочатку перевіряють Content-Type і Content-Encoding, потім ліміт 16384 байти, UTF-8/JSON, поля, параметри й бізнес-правила. Для chunked-запиту байти рахуються під час читання. Після перевищення ліміту сокет зберігається для надсилання JSON 413. GET/HEAD/DELETE не читають тіло як дані API.

URL має lowercase http/https, hostname і довжину до 2048 до та після WHATWG-нормалізації. Облікові дані, сирі пробіли, керівні символи та зворотні косі риски заборонено. Адреси не завантажуються сервером і не перевіряються через DNS. Параметри пагінації — канонічні десяткові числа; невідомі та повторні ключі дають 400.

Усі SQL-значення параметризовані. shortUrl будується з PUBLIC_BASE_URL, а не з Host клієнта. BIGINT clicks/total передаються рядками; createdAt — UTC ISO 8601. Пагінація й total отримуються одним SQL-запитом з одного MVCC-знімка. Сортування доповнено числовим id для однакових дат створення.

Наявні async-помилки автоматично надходять до middleware Express 5. Помилки БД з'єднання/тайм-ауту дають 503, інші SQL-помилки — 500. Відповіді не розкривають SQL, пароль або стек. Єдині Error, Cache-Control: no-store, 405 з Allow та порожні HEAD/204/302 перевіряються окремо.

## Перенаправлення та збереження

GET /r/{code} використовує один атомарний UPDATE clicks = clicks + 1 RETURNING. Немає окремого читання та перезапису лічильника, які втрачали б переходи. HEAD зареєстровано окремо і лише читає адресу. Після успішного SQL повертаємо порожній 302 з Location; при помилці SQL перенаправлення немає. No-store потрібен через змінюваний originalUrl і підрахунок переходів.

PostgreSQL зберігається в іменованому volume. Перевірка `scripts/verify.mjs` читає всі рядки, виконує `docker compose down`, потім `docker compose up -d --wait` і порівнює повний SQL-знімок, включно з id, code, original_url, created_at і clicks. Volume не видаляється.

## Перевірки

24.11.2026 виконано Try it out → Execute у вбудованому браузері для кожної операції. Згенеровані команди збережені в кореневому `test.txt` з назвами curl і без вимірювань часу. У цьому файлі окремо позначено додаткові HTTP-команди, які форма Swagger UI не може створити.

Звичайна форма Swagger UI перевіряє pattern code до надсилання й пропонує тільки application/json. Крім того, браузер автоматично проходить 302, тому для локальної цілі /health у блоці Server response видно фінальний 200. Це обмеження тестового клієнта. Реальні 302, 415 та відхилені формою некоректні параметри підтверджено незалежними HTTP-запитами. Інструкція для отримання знімків у Swagger UI та Network — [swagger-screenshots.md](swagger-screenshots.md).

`npm test` виконує інтеграційні перевірки реального сервера, включно з конкурентними запитами, реальними 500/503 і збереженням усіх даних після down/up. Повний перелік перевірок — `verification-results.json`. Тест створює ресурси з унікальним префіксом і видаляє лише власні. Для 500 тимчасово перейменовує таблицю і відновлює її у finally; для 503 зупиняє БД та відновлює Compose у finally. Цей сценарій призначений для локальної лабораторної БД; під час його запуску сервіс тимчасово недоступний.

Перша перевірка через Swagger виявила некоректний виклик none для SELECT advisory-блокування. Виправлено на one, бо SELECT повертає один рядок; потім успішно перевірено створення та одночасні повтори. Синтаксична перевірка `npm run check` і Redocly проходять; чотири попередження лінтера обґрунтовано в матеріалах частини 2 й вони не змінилися.
